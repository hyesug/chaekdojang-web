# 고해상도 명반 분석 설계

## 왜 하는가

지금까지는 이렇게 답했다.

```
출생명반 → 대운 → 연운 → "2027년에 이직운이 있습니다"
```

앞으로는 이렇게 답한다.

```
출생명반 → 장기 운 → 연 → 월 → (필요하면 일)
  → 여러 체계의 타이밍 교차 → 사건 후보 분류 → 사건 속성
  → 현실 변수 변환 → 지역·조직·관계의 초구체화
```

**프롬프트를 과감하게 써서 구체적인 말을 뽑아내는 방식이 아니다.** 초구체화에
필요한 점술 계산 데이터를 실제로 더 만들고, 계산값과 추론을 구획으로 갈라
모델에게 넘긴다.

### 용신·희신을 넣지 않은 이유

억부·조후·통관·병약 가운데 무엇을 쓰느냐에 따라 용신이 갈리고, 같은 억부법
안에서도 신강·신약 판정 기준이 유파마다 다르다. 어느 쪽이 맞다고 우리가
정할 근거가 없고, 한쪽을 고르면 그 뒤의 모든 월별 판정이 그 선택에 매달린다.
**검증되지 않은 계산식을 만들어 넣지 않는다**는 원칙에 따라 넣지 않았다.
대신 월별 오행 변화를 그대로 싣는다 — 어느 기운이 늘고 주는지는 계산값이다.

## 2. 새로 넣은 계산의 유파 기준

유파에 따라 갈리는 계산은 **한 가지 기준을 골라 처음부터 끝까지 그것만** 쓴다.
기준은 각 모듈 맨 위 주석에도 같은 내용으로 적혀 있다.

| 계산 | 고른 기준 | 갈리는 다른 기준 |
|---|---|---|
| 삼합 부분결합 | 왕지(子午卯酉) 포함 둘 = 반합, 나머지 둘 = 가합(무게 낮춤) | 둘이면 무조건 반합 |
| 방합 | **세 지지가 다 모였을 때만** 인정 | 둘만으로도 반방합 인정 |
| 자미 대한 시작 나이 | 오행국 수 (수2·목3·금4·토5·화6), 세는나이 | 만 나이 기준 |
| 자미 대한 방향 | 양남음녀 순행 / 음남양녀 역행, 명궁에서 출발 | 신궁 출발 |
| 자미 유년 명궁 | 그 해 태세 지지가 있는 궁 | 소한(小限) 기준 |
| 자미 유년 경계 | 입춘 기준 사주 연도 (사이트 전체와 동일) | 음력 정월 초하루 |
| 자미 유월 명궁 | 두군법 — 태세궁에서 정월 기산 역행 생월, 거기서 자시 기산 순행 생시 | 유년 명궁에서 단순 순행 |
| 자미 사화 기준 천간 | 생년=생년간, 대한=대한 명궁 궁간, 유년=태세간, 유월=유월 명궁 궁간 | 유월에 월간 사용 |
| 진행 각(ASC/MC) | 일도일년법 — 진행 날짜의 **출생과 같은 시각** 항성시 | 나이보드·솔라아크 |
| 솔라 리턴 장소 | 거주지 좌표 | 출생지 좌표 |
| 다샤 하위 구간 | 비례 배분, 상위 구간 주인부터 시작 | 동일 |
| 다샤 한 해 길이 | 365.2425일 (사이트 전체와 동일) | 360일 / 365.25일 |
| 바르가 | 파라샤라 표준 (D2 호라·D4 차투르탐샤·D9 나밤샤·D10 다샴샤) | 자이미니 변형 |
| 행성 황위 | 0으로 둠 (엔진이 황경만 계산) | 실제 황위 사용 |

## 3. 구조

```
engine.js / systems/*.js / forecast.js        ← 기존 계산. 건드리지 않음
        │
        ├─ hires/relations.js   간지 관계 (방합·투간·지장간 활성·층 교차)
        ├─ hires/bazi.js        원국×대운×세운×월운(×일진)
        ├─ hires/ziwei.js       원국·대한·유년·유월 12궁 + 네 층 사화
        ├─ hires/western.js     트랜싯·2차 프로그레션·솔라 리턴
        ├─ hires/vedic.js       MD/AD/PD/SD·고차라·D1/D2/D4/D9/D10
        ├─ hires/location.js    아스트로카토그래피·로컬스페이스·릴로케이션·지리
        │
        └─ hires/grid.js        ↑ 를 같은 시간 축(절기월)에 나란히 놓음
                    │            **여기까지가 계산. 해석하지 않는다.**
                    ↓
              hires/events.js   사건 추론 (LEVEL 2~5)
                    ↓
              hires/router.js   질문 → 계산 계획
              hires/context.js  구조화 JSON + 프롬프트용 글
                    ↓
        ai.js → app/fortune-ai/route.ts → Claude
        hires/panel.js → 화면에서 펼쳐 보기
```

`grid.js` 위쪽은 계산만, `events.js` 아래쪽은 해석만 한다. 한 파일에 섞으면
나중에 무엇이 계산이고 무엇이 추측인지 가릴 수 없게 된다.

## 4. 사건 추론 다섯 층

| 층 | 무엇 | 만드는 곳 |
|---|---|---|
| LEVEL 1 계산값 | 간지·궁·행성·다샤. 천문·역법에서 그대로 나온 값 | `grid.js` |
| LEVEL 2 활성 분야 | 직업·재물·관계·결혼·주거·이사·건강·학업 | `events.js` `scoreMonth` |
| LEVEL 3 사건 후보 | 이직·승진·직무변경·조직개편·퇴사·창업 … | `events.js` `candidatesOf` |
| LEVEL 4 사건 속성 | 자발/비자발 · 경력유지/전환 · 확대/축소 · 보상/환경 · 근거리/장거리 · 안정형/성장형 | `events.js` `attributesOf` |
| LEVEL 5 초구체화 | 최강 구간 → 월 · 국면(준비·발생·확정·정착) · 방향 → 후보 생활권 · 사건 선후 | `events.js` + `location.js` |

### 시간 구간 점수화

각 절기월마다 네 핵심 체계가 낸 신호를 무게 붙여 더한다. 그 합은 **바깥으로
나가지 않는다.** 그 사람의 그 기간 안에서 순위를 매겨 네 등급으로만 바꾼다.

```
최강 (상위 8%) · 강함 (~25%) · 보조 (~55%) · 약함 (나머지)
```

절대 점수를 쓰지 않는 이유는 기존 다층 해석 레이어와 같다. 달마다의 값이
원래 가운데에 몰려 있어서, 절대 기준을 쓰면 열두 달 중 열 달이 '적기'가 된다.

### 국면 분리

하나의 운을 "이직운" 한 마디로 묶지 않는다. 각 달의 신호 성질로 가른다.

| 국면 | 무엇이 켜졌을 때 |
|---|---|
| 준비기 | 인성(문서·학습)·경쟁 신호 |
| 발생기 | 충·역마·천왕성·화기 — 흔들고 옮기는 신호 |
| 확정기 | 합·정관·화록·제도화 신호 |
| 정착기 | 전택·4하우스·안정 신호 |

1등과 2등이 거의 같으면 국면을 정하지 않는다. 억지로 붙이지 않는다.

## 6. 질문별 계산 파이프라인

모든 질문에 모든 계산을 돌리지 않는다. `router.js` 가 낱말로 분야를 가려
필요한 계산만 켠다. 못 가려내면 기본 분야로 돌리고 **그 사실을 문맥에 적는다** —
엉뚱한 분야를 골라 그럴듯하게 답하는 것보다 낫다.

| 질문 | 켜지는 계산 |
|---|---|
| 올해 이직할까 | 세운·월운 + 대한·유년·유월 + 트랜싯·솔라리턴·프로그레션 + 다샤·D10·고차라 |
| 언제 결혼할까 | 부처궁 층 + D9 + 7하우스·금성·목성 트랜싯 + 다샤 + 관련 월운 |
| 어느 도시가 좋은가 | 릴로케이션 + 아스트로카토그래피 + 로컬스페이스 + 전택·천이 층 + D4 |
| 계약 날짜 | 위 + 일진 층 |

## 7. 문맥 전달

명반 본문(`buildContext`)은 한 사람에 대해 고정이라 그대로 두고 **캐시에 태운다.**
고해상도 구획은 질문마다 달라지므로 **별도 덩이(`focus`)로 보내고 캐시에 태우지
않는다.** 두 번째 질문부터 명반 본문은 캐시에서 읽히고 고해상도만 새로 들어간다.

- `route.ts` `MAX_CONTEXT_CHARS` 24,000 → 60,000
- `route.ts` `MAX_FOCUS_CHARS` 40,000 (신규)

## 8. 할루시네이션 방지

프롬프트(`route.ts`)와 문맥(`context.js`) 양쪽에서 같은 것을 막는다.

- 계산하지 않은 트랜싯·월운·다샤를 있는 것처럼 말하기
- 특정 도시·동네가 명반에서 직접 나왔다고 말하기
- 특정 기업 이름을 미래의 직장이라고 말하기
- 직원 수·연봉 액수를 계산값처럼 제시하기
- 사용자가 알려준 현실 정보를 명반이 맞힌 것처럼 되돌려 말하기
- 지난 대화를 근거로 "예언이 맞았다"고 말하기
- 근거 없는 확률 숫자 만들기

문맥에 적히지 않은 달·구간·라인·도시는 만들어내지 못하게 하고, 좁히지 못한
속성은 "근거가 얇다"고 적는 것이 답의 일부라고 못박는다.
