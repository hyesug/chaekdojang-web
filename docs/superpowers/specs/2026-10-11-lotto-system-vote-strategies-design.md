# 로또 15체계 득표 기반 6개 번호 전략

## 목적

기존 15체계 후보 슬롯 계산과 A·D·E·F·H 예측은 변경하지 않는다. 그 슬롯을 입력으로만 사용하는 세 가지 고정 6개 번호 전략을 추가해, 1246회부터 추첨 전 저장하고 기존 모델과 동일한 방식으로 적중 수를 비교한다.

새 저장 모델 코드는 기존 A와 혼동되지 않도록 `S1`·`S2`·`S3`으로 한다. 화면 표기는 각각 `전략 A`·`전략 B`·`전략 C`으로 한다.

## 입력과 공통 규칙

- 입력은 `predictor.ts`의 현행 `candidateValues(features)`가 반환하는 15체계의 원본 후보 슬롯이다. 슬롯 내용, 슬롯 순서, 기존 후보 계산식과 기존 A·D·E·F·H 산출은 수정하지 않는다.
- 번호의 **원본 슬롯 득표수**는 같은 번호가 원본 후보 슬롯에 등장한 횟수다.
- 번호의 **체계 지지 수**는 그 번호를 한 번 이상 낸 서로 다른 체계 수다. 한 체계 안의 중복 슬롯은 체계 지지 수를 한 번만 센다.
- 모든 비교의 마지막 동률 기준은 번호 오름차순이다. 이 기준은 과거 검증과 미래 저장 모두에 고정한다.
- 선택 결과는 오름차순으로 정렬한 서로 다른 6개 번호로 저장한다. 순위 결정에는 아래의 순위를, 저장 표현에는 번호 오름차순을 사용한다.
- 현행 15체계 후보 슬롯 계약상 합집합이 6개 이상이어야 한다. 구현은 이 불변식을 검사해 위반 시 생성 실패로 처리한다. 후보 밖 번호를 임의로 채우지 않으며, 사후 보정도 하지 않는다.

## 세 전략

| 저장 코드 | 화면명 | 순위 키(앞이 우선) |
| --- | --- | --- |
| `S1` | 전략 A: 원본 슬롯 득표순 | 원본 슬롯 득표수 내림차순 → 번호 오름차순 |
| `S2` | 전략 B: 2표 이상 우선 | 득표 그룹(2표 이상 우선, 1표 다음) → 각 그룹의 원본 슬롯 득표수 내림차순 → 번호 오름차순 |
| `S3` | 전략 C: 체계 지지와 득표 결합 | 체계 지지 수 내림차순 → 원본 슬롯 득표수 내림차순 → 번호 오름차순 |

각 전략은 위 순위의 상위 6개만 선택한다. `S2`에서 2표 이상 번호가 6개 이상이면 그 안에서만 6개를 선택하고, 부족한 경우에만 1표 번호로 채운다.

## 저장과 검증

- 1243~1245회는 코드의 회귀 검증용 고정 fixture로만 사용한다. 이 회차의 DB 저장값·활성 상태·revision은 만들거나 바꾸지 않는다.
- fixture는 각 회차의 추첨 전 이벤트 입력과 그 시점까지의 이력으로 세 전략을 한 번 산출하고, 6개 티켓과 당첨번호 교집합을 기대값으로 고정한다. 3회 결과에 맞춰 규칙, 동률, 티켓을 조정하지 않는다.
- 1246회부터 새 prediction round를 생성할 때 기존 A·D·E·F·H와 `S1`·`S2`·`S3`을 같은 revision, 같은 `generated_at`, 같은 사유로 함께 저장한다. 추첨 시각 이후에는 기존 확정 규칙을 그대로 적용한다.
- 재생성은 기존과 같은 revision 규칙을 유지한다. 이전 활성 행은 비활성화하고, 새 전략을 포함한 전체 8개 티켓을 같은 새 revision으로 저장한다.
- `model_version`과 `source_commit`은 생성 코드가 제공하는 값으로 저장해 산출 코드를 추적한다. 저장 후 당첨 결과를 참고해 티켓을 바꾸는 경로는 추가하지 않는다.

## 계약 및 마이그레이션

- PostgreSQL `lotto_future_predictions.model`의 CHECK 제약을 additive migration으로 `A,D,E,F,H,S1,S2,S3` 허용으로 확장한다. 기존 행은 수정하거나 재기록하지 않는다.
- 백엔드의 고정 모델 목록과 삽입 검증을 8개 모델로 확장한다. 조회 응답의 기존 필드와 적중 수 계산은 그대로 둔다.
- 내부 생성 API는 8개 티켓을 모두 전달한다. 프론트엔드 응답 타입·관리자 비교 화면은 세 코드와 화면명을 인식하되, 기존 표시·필터·저장 데이터 의미를 바꾸지 않는다.

## 구현 경계

- 웹: 후보 슬롯을 체계 식별자와 함께 집계하는 순수 selector를 `lib/lotto-future/predictor.ts` 인근에 추가하고, `generateFrozenPredictions` 반환에 `S1`·`S2`·`S3`만 더한다.
- API: migration, 허용 모델 상수, 관련 계약 테스트만 변경한다.
- 데이터 backfill, 기존 prediction 수정, 결과에 따른 가중치 학습, 새 외부 데이터 수집은 범위 밖이다.

## 검증 계획

1. selector 단위 테스트: 원본 득표, 체계 지지 수, 각 순위 키, 마지막 번호 오름차순 동률, 정확히 6개·중복 없음·번호 범위를 검증한다.
2. 1243~1245 fixture 테스트: 세 회차의 입력으로 6개 티켓과 당첨 교집합이 고정값과 일치하는지 검증한다.
3. 기존 predictor 테스트: A·D·E·F·H 기대값이 변하지 않고 8개 모델이 모두 유효한 티켓을 반환하는지 검증한다.
4. API 테스트: 8개 모델 저장·조회, 새 CHECK 제약, 1246회 이후 생성 시점/확정 전후 규칙을 검증한다.
5. 전체 관련 테스트와 정적 검사 후, 운영 DB에서는 migration 적용 전후 기존 행 수·모델값이 변하지 않는지 확인한다.
