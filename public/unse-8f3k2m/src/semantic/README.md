# 의미축 해석 엔진 (`src/semantic/`)

열다섯 체계의 전통 해석을 **현실 질문**으로 옮기는 층입니다.
성격 설명을 만드는 곳이 아니라, "무슨 일을 할 사람인가 · 결혼은 이른 편인가"에
**구조화된 숫자**로 답하는 곳입니다.

기존 `hires/interpret.js` 는 그대로 둡니다. 이 폴더는 그 위에 얹는
**별도 출력 경로**이고, 화면과 AI 문맥이 쓰던 길은 건드리지 않았습니다.

---

## 일곱 층

```
LEVEL 1  15체계 원시 계산       engine.js · hires/
LEVEL 2  체계별 전통 해석        extract.js → rules.js → systems.js
LEVEL 3  공통 의미축            axes.js (+ lexicon.js)
LEVEL 4  현실 결과 카테고리       categories.js
LEVEL 5  15체계 종합            ensemble.js (+ reliability.js)
LEVEL 6  실제 사례 검증·보정      ../validation/ · scripts/validate-semantic.mjs
LEVEL 7  시기운 결합            timing.js  ← 이음매만 있고 비어 있습니다
```

| 파일 | 하는 일 |
|---|---|
| `axes.js` | 의미축 정의. 모든 축은 **0~1 지지도** 하나로 통일 |
| `lexicon.js` | 전통 문구의 **낱말**을 축으로 옮기는 단 하나의 사전 |
| `rules.js` | 해석 규칙 등록소. 기호 → 축 기여 (`source`, `confidence` 포함) |
| `extract.js` | 체계마다 "그 전통이 지정한 자리"의 기호를 꺼냄. 계산은 안 함 |
| `systems.js` | 체계별 구조화 해석 + 근거(evidence) |
| `categories.js` | 축 → 업종·고용형태·결혼시기 등 **분포** |
| `reliability.js` | 전통 무게 · 실측 무게 · 침묵 규칙 |
| `ensemble.js` | **축에서** 합침 (범주에서 합치지 않음) |
| `timing.js` | 원국 susceptibility + 결혼 시기 곡선(뼈대는 통계) |
| `narrate.js` | 구조화 결과 → 문장. 모델은 다듬기만 함 |

## 이 설계가 답하려는 실패

이 저장소는 융합을 **세 번 만들어 세 번 다 실패**했습니다.

| 만든 것 | 결과 |
|---|---|
| `profile.js` 융합 | 다섯 명 전원에게 같은 답 |
| 가중투표 융합 | 열한 명 중 여덟에게 "전문가" → 2/11 |
| 교집합 융합 | 어떤 기준으로도 영점을 못 넘음 |

셋의 공통점은 **범주(label)에서 합쳤다**는 것입니다. 범주에서 합치면 넓은
범주로 표가 쏠립니다. 그래서 여기서는 **축에서 합칩니다** — 자미가 미적감각을,
사주가 기술을 가리키면 두 축이 **둘 다 선 벡터**가 되고, 범주는 합쳐진 벡터를
보고 한 번만 고릅니다.

**이것이 옳다는 보장은 없습니다.** 이전 실패의 원인을 구조적으로 비껴갈 뿐이고,
실제로 나은지는 LOO 가 말합니다. 합친 것이 최고 단독 체계보다 나쁘면 그대로 적습니다
(**현재 실제로 그렇습니다** — 아래 참조).

## 규칙을 고칠 때 — 반드시 지킬 것

```
한 사례의 오답을 맞히기 위한 규칙 추가 금지.

동일한 방향의 오류가 여러 독립 사례에서 반복될 때만
해석 규칙 수정 후보로 본다.

실제 데이터를 본 뒤 수정한 규칙은
반드시 그 사례를 제외한 검증(LOO)에서도 개선되는지 확인한다.
```

- `lexicon.js` 의 낱말 무게는 **그 낱말이 한국어에서 뜻하는 바**이지 사례의
  정답이 아닙니다.
- `categories.js` 의 `SHARPNESS`, `OTHER_FLOOR`, `MIN_P` 는 자유 모수입니다.
  **열한 명을 보고 고르지 않았습니다.** 바꾸면 LOO 를 다시 돌립니다.
- `occupations.js`(정답 정의)는 엔진이 보지 않습니다. 고쳐도 예측은 안 바뀌고
  **채점 기준만** 바뀝니다.

## 침묵하는 자리

실측이 영점보다 나빴던 축은 **답하지 않습니다.** 그 판단은
`hires/interpret.js` 의 `AXIS_OWNER` 한 곳에서만 정하고, 여기서는 읽어 옵니다.

| 막힌 것 | 이유 |
|---|---|
| `residence.ownership` (자가/임차) | 말한 4명 중 2 — 영점 71%보다 나쁨 |
| `relationship.stability` / `volatility` | 5명 중 3 — 영점 75%보다 나쁨 |
| `career.tempo` (안정형/변동형) | 열다섯을 다 재도 순열검정 p=0.423 |
| 사건 날짜 | 달 p=0.868 · 해 p=0.196 — 두 자료에서 다 짐 |

건강은 범주 자체를 만들지 않습니다. 질환명·수술 여부를 뜻하는 칸이 생기는
순간 엔진이 그것을 맞히려 들고, 의료 판단처럼 읽힙니다.

## 지금 성적 (11명 · 사람 단위 LOO)

```
career.industry (16칸)   로그손실   top1   순위백분위
  합침                     2.840  0.091       0.512
  고르게 찍기               2.773      0       0.500
  한계분포                  3.006      0       0.403
  남의 명반                 2.850  0.091       0.518   ← 합침과 구별되지 않음
  순열검정 p = 0.479
  [대조] '열다섯 중 하나라도 1위' = 0.73   ← 예측력이 아님
```

**합친 것이 고르게 찍기보다 나쁘고, 남의 명반과 구별되지 않습니다.**
체계 단독으로는 자미두수가 로그손실 2.384 · top1 0.375(n=8)로 가장 나았지만,
**열다섯을 늘어놓고 제일 잘한 것을 고르는 일** 자체가 우연을 고르는 일입니다
(`validate-axes.mjs` 주석 참조). 담당으로 승격하지 않았습니다.

16칸 분포에 11명이면 **칸당 0.7명**입니다. 지금 숫자로는 아무것도 맞았다고
말할 수 없고, 그것이 이 층의 현재 정직한 결론입니다.

```bash
node validation/build-people.mjs     # 사례 파일 → 정답표 (개인정보, 커밋 안 함)
node scripts/validate-semantic.mjs   # 사람 단위 LOO
npm run test:unse                    # 정직성 검사 23개
```
